# 头脑风暴流程 (Brainstorming)

## 1. 概述

本技能定义了一套系统化的需求分析和方案设计流程，帮助开发者在编码前对问题进行充分思考，产出高质量的技术方案。

---

## 2. 适用场景

- 接到新的功能需求，需要确定实现方案
- 遇到技术难题，需要探索多种解决路径
- 项目初期进行技术选型和架构设计
- Code Review 时讨论改进方向

---

## 3. 流程步骤

### 第一步：问题定义 (Problem Definition)

#### 3.1.1 明确目标
回答以下问题：
```
1. 我们要解决什么问题？（一句话描述）
2. 谁会从这个功能中受益？（目标用户/系统）
3. 成功的标准是什么？（可量化的指标）
4. 有什么限制条件？（时间、资源、技术栈）
```

#### 3.1.2 问题描述模板
```markdown
## 问题描述

**背景**: [为什么需要这个功能/解决这个问题]

**目标**:
- 功能目标: [这个功能要做什么]
- 用户目标: [用户通过这个功能能完成什么]
- 业务目标: [对业务的价值是什么]

**约束条件**:
- 技术栈限制: [必须使用的技术]
- 时间限制: [DDL 或预期时间]
- 性能要求: [响应时间、吞吐量等]
- 兼容性要求: [浏览器/Node 版本等]

**成功指标**:
- [ ] 指标1: [具体数字]
- [ ] 指标2: [具体数字]
```

---

### 第二步：调研与分析 (Research & Analysis)

#### 3.2.1 现状分析
```markdown
## 现状分析

**现有系统**:
- 相关模块: [有哪些现有代码与此相关]
- 数据流: [当前数据如何流转]
- 痛点: [当前存在的具体问题]

**竞品/参考**:
- [参考项目/产品1]: [可借鉴的点]
- [参考项目/产品2]: [可借鉴的点]
```

#### 3.2.2 利益相关者
| 角色 | 关注点 | 优先级 |
|------|--------|--------|
| 终端用户 | 易用性、响应速度 | 高 |
| 运维人员 | 稳定性、可监控 | 中 |
| 开发团队 | 可维护性、扩展性 | 高 |

---

### 第三步：方案生成 (Solution Generation)

#### 3.3.1 方案模板
每个候选方案应包含：
```markdown
## 方案 N: [方案名称]

**核心思路**: [一句话描述]

**优势**:
- [优点1]
- [优点2]

**劣势**:
- [缺点1]
- [缺点2]

**技术栈**: [涉及的技术/库]

**实现概要**:
1. [步骤1]
2. [步骤2]
3. [步骤3]

**风险评估**: [高/中/低]
- [风险点及缓解措施]

**工作量估算**: [人天]
```

#### 3.3.2 发散思维技巧
- **类比法**: 类似问题在其他领域是如何解决的？
- **逆向思维**: 如果不考虑限制，最优方案是什么？
- **组合创新**: 能否结合多个方案的优点？
- **极端简化**: 最简可行方案（MVP）是什么？

---

### 第四步：方案评估 (Solution Evaluation)

#### 3.4.1 评估矩阵

| 维度 | 权重 | 方案A | 方案B | 方案C |
|------|------|-------|-------|-------|
| 实现复杂度 | 20% | 3/5 | 4/5 | 2/5 |
| 可维护性 | 25% | 4/5 | 3/5 | 3/5 |
| 性能 | 20% | 4/5 | 3/5 | 5/5 |
| 扩展性 | 20% | 3/5 | 4/5 | 4/5 |
| 开发效率 | 15% | 4/5 | 3/5 | 2/5 |
| **加权总分** | 100% | 3.6 | 3.4 | 3.2 |

#### 3.4.2 决策检查清单
- [ ] 方案是否满足所有功能需求？
- [ ] 方案是否在约束条件内可行？
- [ ] 方案是否与现有架构兼容？
- [ ] 方案是否有明确的失败处理策略？
- [ ] 团队成员是否理解并认可方案？

---

### 第五步：方案细化 (Solution Refinement)

#### 3.5.1 技术方案文档模板
```markdown
# [功能名称] 技术方案

## 1. 概述
[简要描述方案目标和核心思路]

## 2. 架构设计

### 2.1 系统交互图
```
[调用者] → [API 层] → [Service 层] → [数据层]
                ↓
          [外部服务]
```

### 2.2 核心数据结构
```typescript
interface FeatureRequest {
  field1: string;
  field2: number;
}

interface FeatureResponse {
  id: string;
  status: 'pending' | 'completed';
  result: Record<string, unknown>;
}
```

## 3. 接口设计

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/v1/feature | 创建 |
| GET | /api/v1/feature/:id | 查询 |
| PUT | /api/v1/feature/:id | 更新 |

## 4. 关键流程
[流程图或时序图描述核心业务流程]

## 5. 异常处理
| 异常场景 | 处理方式 | 用户提示 |
|----------|----------|----------|
| 网络超时 | 重试3次 + 降级 | "请求超时，请重试" |
| 数据不存在 | 返回404 | "数据不存在" |

## 6. 测试策略
- 单元测试: [覆盖哪些模块]
- 集成测试: [覆盖哪些流程]
- 边界测试: [关键边界条件]

## 7. 上线计划
- 开发阶段: [起止时间]
- 测试阶段: [起止时间]
- 灰度发布: [策略]
- 全量上线: [时间]

## 8. 监控指标
- [ ] 接口响应时间 P99 < 200ms
- [ ] 错误率 < 0.1%
- [ ] 功能使用率监控
```

---

### 第六步：评审与迭代 (Review & Iterate)

#### 3.6.1 评审会议议程
1. **方案讲解** (10 min) — 方案负责人讲解核心思路
2. **提问澄清** (10 min) — 参与者提问，确保理解一致
3. **优缺点讨论** (15 min) — 列出方案的优缺点
4. **替代方案** (10 min) — 是否有更好的方案
5. **决策与行动** (5 min) — 确定方案及下一步行动

#### 3.6.2 迭代原则
- 方案不是一成不变的，实施过程中发现的问题应及时反馈
- 小步快跑，优先实现核心流程，逐步完善
- 保持方案文档更新，确保文档与实现一致

| 工具 | 用途 |
|------|------|
| **Draw.io / Excalidraw** | 架构图、流程图绘制 |

| **PlantUML** | UML 图表生成 |

---

## 5. 反模式

❌ **避免**:
- 跳过问题定义直接开始编码（"先写代码再说"）
- 只考虑一个方案不做对比
- 方案文档过于简略，缺乏关键细节
- 忽视非功能性需求（性能、安全、可维护性）
- 方案评审走过场，没有实质讨论

---

## 6. 快速启动

当需要头脑风暴时，只需说：
> "我们来头脑风暴一下 [问题/需求]"

AI 助手将按照上述流程，逐步引导你完成问题定义、方案生成和评估。
